# Meditation PWA на Astro с офлайн-аудио

## TL DR

Предлагается создать статический одностраничный сайт медитаций на Astro и daisyUI и опубликовать его на GitHub Pages. Локальный аудиофайл, Web App Manifest и service worker превратят сайт в устанавливаемую PWA: после первого успешного открытия пользователь сможет запускать и останавливать медитацию без сети, а Media Session API и нативное воспроизведение аудио обеспечат работу в фоне там, где это разрешают мобильные ОС. MVP намеренно ограничен одним треком и одним действием, без аккаунтов, серверной части и внешних потоковых сервисов.

## Контекст

Сейчас репозиторий содержит только README с идеей приложения, поэтому существующего кода, спецификаций и архитектурных ограничений нет. Нужен аналог простого сценария Tide, но YouTube не подходит как источник воспроизведения: поток требует сети и не даёт надёжного офлайн-режима, а использование записи требует прав на аудио. Поэтому реализация должна объединить статическую генерацию Astro, локально опубликованный аудиофайл и PWA-возможности браузера; GitHub Pages обеспечит HTTPS-хостинг без отдельного backend.

Первый запуск при отсутствии сети невозможен: сначала страница, service worker и аудиофайл должны быть загружены по сети, а service worker — установлен и активирован. После этого все ресурсы основного сценария должны быть доступны локально.

В README упоминается «SSH»; по первой строке и общему контексту RFC исходит из того, что имелся в виду SSG.

## Назначение и цели

Цель — дать мобильному пользователю минимальный и надёжный способ начать медитацию: установить сайт на домашний экран, нажать «Начать», слушать непрерывный трек и нажать «Стоп», в том числе после перехода в офлайн и блокировки экрана.

- Сократить основной сценарий до одного экрана и одной основной кнопки.
- Убрать зависимость воспроизведения от сети и сторонних аудиоплееров после первоначальной установки PWA.
- Использовать нативные возможности мобильного браузера вместо native-обёртки и собственного backend.
- Обеспечить воспроизводимую публикацию статического сайта на GitHub Pages, включая размещение в подпути репозитория.
- Оставить после реализации актуальные README.md с описанием приложения и AGENTS.md с контекстом, необходимым агентам для безопасной дальнейшей разработки.

Заинтересованные стороны: мобильные пользователи приложения; maintainer репозитория; ревьюеры frontend/PWA-решения; владелец прав на аудио и автор метаданных трека; coding-агенты, которые будут развивать проект по AGENTS.md. Ревью должны пройти предлагаемая архитектура, офлайн-стратегия и критерии проверки на реальных устройствах.

В MVP не входят библиотека треков, таймеры и статистика медитаций, аккаунты, синхронизация, push-уведомления, аналитика, потоковое воспроизведение YouTube, социальные функции и нативные приложения для магазинов.

## Составляющие и особенности

Решение разбито по непересекающимся подсистемам: интерфейс, воспроизведение, офлайн-оболочка и публикация. Порядок ниже одновременно является порядком реализации и приёмки.

### 1. Статический интерфейс медитации

Astro формирует полностью статический сайт с одной страницей `src/pages/index.astro`. Для интерактивности используются клиентский TypeScript и стандартные Web API; React или другой UI-фреймворк не нужен. daisyUI подключается через используемую им актуальную интеграцию с Tailwind CSS/Astro, версии фиксируются в lockfile.

Предлагаемая структура:

- `src/components/MeditationPlayer.astro` — разметка проигрывателя и доступные подписи;
- `src/scripts/player.ts` — состояние и события воспроизведения;
- `src/styles/global.css` — базовые стили и настройки темы;
- `public/icons/` — иконки приложения;
- `public/audio/meditation.mp3` — финальный локальный трек после подтверждения прав.

Экран содержит название практики, спокойную статическую обложку, крупную кнопку «Начать»/«Стоп» и текстовый статус: загрузка, готовность, воспроизведение, остановка или ошибка. Дополнительно показываются короткая подсказка об установке и понятное сообщение, если браузер не поддерживает нужную возможность. Установка оформляется через нативный запрос браузера там, где он доступен; для iOS даётся инструкция «Поделиться → На экран “Домой”».

Интерфейс mobile-first, работает без горизонтальной прокрутки и масштабируется на планшет и desktop. Основное действие доступно с клавиатуры и screen reader, имеет видимый focus, достаточный контраст и область нажатия не менее 44×44 CSS px. Анимации необязательны и отключаются при `prefers-reduced-motion`.

### 2. Локальное воспроизведение и фоновый режим

Используется один HTML `<audio>`-элемент с локальным URL внутри `base` сайта. Воспроизведение начинается только по явному нажатию: приложение не пытается обходить запрет autoplay. Трек зацикливается для непрерывной медитации. «Стоп» приостанавливает аудио и возвращает позицию в начало; следующее нажатие «Начать» запускает практику сначала.

Модуль воспроизведения:

- обрабатывает Promise из `audio.play()`, включая отказ autoplay и отсутствие файла;
- синхронизирует кнопку и текст с событиями `play`, `pause`, `waiting`, `canplay`, `error`, а не предполагает успех до фактического старта;
- настраивает Media Session API: название, исполнителя/приложение, обложку и доступные действия `play`, `pause`, `stop`;
- отражает внешние паузы, например звонок или переключение аудиосессии, чтобы UI не показывал ложное воспроизведение;
- не использует таймеры или цикл JavaScript для поддержания звука в фоне — звук продолжает воспроизводить нативный media stack ОС.

Аудио хранится в репозитории или добавляется в release-процесс как явно лицензированный локальный asset; приложение не скачивает его с YouTube и не обращается к YouTube во время работы. До получения финального файла допускается лицензированный placeholder только для разработки, но критерий готовности MVP требует согласованного трека и корректных метаданных.

Целевые платформы — актуальные стабильные Safari на iOS и Chrome на Android, в режиме установленной PWA. Фоновое воспроизведение проверяется на реальных устройствах: эмулятор и DevTools недостаточны. ОС может прервать звук при звонке, смене аудиофокуса, нехватке ресурсов или агрессивном энергосбережении; такие системные прерывания не маскируются и не считаются гарантированно устранимыми веб-приложением.

### 3. Установка и полный офлайн-контур

PWA реализуется через `@vite-pwa/astro` и Workbox в конфигурации Astro. Service worker предкэширует собранные HTML/CSS/JS, иконки, Web App Manifest и `meditation.mp3`. Лимит `maximumFileSizeToCacheInBytes` явно устанавливается выше размера итогового аудиофайла: стандартное ограничение Workbox не должно молча исключить трек из precache manifest. Навигации внутри `scope` получают закэшированную страницу приложения; сетевые fallback-запросы к внешним сервисам для основного сценария отсутствуют.

Web App Manifest содержит `name`, `short_name`, `description`, `start_url`, `scope`, `display: standalone`, цвета темы и фона, а также PNG-иконки 192×192 и 512×512, включая maskable-вариант. Все пути вычисляются с учётом Astro `base`, чтобы PWA работала и на корневом домене, и по адресу `https://<user>.github.io/<repo>/`.

Для обновлений применяется автоматическая регистрация нового service worker без принудительной перезагрузки страницы во время воспроизведения. Новая версия не должна смешивать ресурсы разных сборок: precache Workbox версионирует assets, а новый интерфейс применяется при следующей навигации или запуске. Удаление старых кэшей выполняется механизмом Workbox после активации новой версии.

Гарантированный офлайн-сценарий начинается после первого полного онлайн-открытия и активации service worker. Если пользователь открывает страницу впервые без сети, аудиофайл не попал в кэш или пользователь очистил site data, приложение честно сообщает, что нужно одно успешное онлайн-открытие; псевдоофлайн через streaming или скрытую загрузку не используется.

### 4. Воспроизводимая публикация на GitHub Pages

Проект собирается командой `npm ci && npm run build` на зафиксированной Active LTS-версии Node.js; та же версия указывается в `.nvmrc` и `actions/setup-node`. Результатом является только статический каталог `dist/`.

GitHub Actions запускает сборку при push в основную ветку и по ручному `workflow_dispatch`. Workflow использует официальные Pages actions для загрузки `dist/` и деплоя, имеет минимально необходимые permissions и не требует персональных токенов. В настройках репозитория Pages использует источник GitHub Actions.

`site` и `base` Astro соответствуют фактическому Pages URL. Проверяются не только ссылки на странице, но и manifest, service worker, иконки, аудио и прямой заход по опубликованному URL. Пользовательский домен необязателен; при его появлении меняется конфигурация URL, но не архитектура.

4. **Воспроизводимая публикация на GitHub Pages.** Настроить Pages workflow и фактические `site`/`base`, затем повторить полную мобильную приёмку на опубликованном HTTPS URL.
5. **Документация продукта и контекст для агентов.** По фактической реализации переписать README.md, создать корневой AGENTS.md и проверить документированные команды на чистом checkout. ## Итого и рекомендации

Рекомендуется реализовать MVP как статическую Astro/daisyUI PWA с одним локальным зацикленным треком, явным Start/Stop, Media Session и полным precache ресурсов. GitHub Pages и Actions достаточны для хостинга и доставки, а отказ от YouTube runtime и backend снимает основные сетевые зависимости. До начала реализации нужно подтвердить права и получить итоговый аудиофайл; до релиза — подтвердить фон и офлайн на реальных iOS и Android, переписать README.md с описанием приложения и заполнить AGENTS.md актуальным контекстом для дальнейшей работы агентов.

## Альтернативные варианты

### Вариант A: Astro PWA с локальным precache-аудио

**Плюсы:** соответствует выбранному стеку; весь основной сценарий работает офлайн; нет backend; статический Pages-деплой; минимальная клиентская логика.

**Минусы:** первый запуск требует сети; размер трека увеличивает установочный кэш; фоновое поведение зависит от браузера и ОС; нужны права на файл.

**Компромиссы:** ради надёжности аудио загружается целиком заранее, а не по мере прослушивания.

### Вариант B: Обычный Astro-сайт с YouTube iframe

**Плюсы:** быстрее подготовить прототип; не нужно хранить аудиофайл.

**Минусы:** не выполняет требования офлайн и управления фоновым звуком; зависит от сети, YouTube и стороннего плеера; не решает вопрос прав.

**Компромиссы:** простота интеграции достигается отказом от ключевого пользовательского сценария, поэтому вариант отклонён.

### Вариант C: Native/Capacitor-приложение

**Плюсы:** шире контроль аудиосессий, фоновых режимов и публикации в магазинах.

**Минусы:** дополнительные SDK, нативные проекты, сертификаты и release-процессы; противоречит цели простого PWA на GitHub Pages.

**Компромиссы:** имеет смысл только если проверки докажут, что требуемый фоновый сценарий невозможен на целевых браузерах; для первого MVP вариант преждевременен.

### Рекомендация по выбору

Выбрать вариант A. Он единственный одновременно сохраняет требуемый Astro SSG/PWA-стек, простой Pages-деплой и проверяемый офлайн-сценарий. Native-обёртку пересматривать только по результатам реальных устройственных испытаний, а YouTube не использовать как runtime-источник.

## Тест инструкции

### 1. Чистая установка и автотесты

- [package.json](../../package.json) — фактические скрипты проверки; Node.js 24 зафиксирован в [.nvmrc](../../.nvmrc).
- В новом окружении выполнить `nvm use && npm ci && npx playwright install chromium`.
- Запустить `npm run test:all`. Ожидаются 0 ошибок Astro/TypeScript, 7 unit-тестов, успешная production-сборка и 8 E2E-тестов.
- [tests/player.test.ts](../../tests/player.test.ts) — Start/Stop, сброс и повторный запуск, отказ `play()`, внешняя пауза, waiting, ошибка и Media Session.
- [tests/e2e/meditation.spec.ts](../../tests/e2e/meditation.spec.ts) — три viewport, клавиатура и область нажатия, локальный loop, отсутствие внешних запросов, base, manifest, precache, offline-reload и инструкции установки.
- [vitest.config.ts](../../vitest.config.ts) и [playwright.config.ts](../../playwright.config.ts) — Vitest не должен собирать E2E-файлы; Playwright собирает сайт с `/medi/` и запускает отдельный static server.

### 2. Production build, корневой путь и precache

- Выполнить `npm run build` и убедиться, что создаётся только статический [dist/](../../dist/), а service worker инициализируется без `non-precached-url`.
- Выполнить `BASE_PATH=/medi/ SITE_URL=https://anatolii-iumashev.github.io npm run build` для проверки Pages-подпути.
- [dist/manifest.webmanifest](../../dist/manifest.webmanifest) — `id`, `start_url`, `scope` и все иконки должны находиться внутри `/medi/`.
- [dist/sw.js](../../dist/sw.js) — precache должен содержать `/medi/`, JS/CSS, три PNG-иконки, обложку и `audio/meditation.mp3`; `navigateFallback` должен ссылаться на закэшированный `/medi/`.
- При сравнении записей Cache Storage учитывать `?__WB_REVISION__=…`: проверять `new URL(url).pathname`, а не окончание полного URL.

### 3. Локальный ручной сценарий

- Выполнить `npm run dev` и открыть [http://localhost:4321/](http://localhost:4321/).
- На ширинах 360, 390 и 768 px проверить отсутствие горизонтальной прокрутки, читаемый live-статус и видимый focus.
- Нажать «Начать»: звук запускается только после действия, кнопка меняется на «Стоп». Нажать «Стоп»: звук прекращается, позиция сбрасывается; повторный запуск идёт с начала.
- Поставить аудио на паузу через системное/браузерное управление: UI должен вернуться к «Начать» без сброса позиции. Заблокировать аудио или удалить доступ к файлу: должен появиться понятный статус ошибки без uncaught exception.

### 4. GitHub Pages

- [Deploy to GitHub Pages](https://github.com/anatolii-iumashev/medi/actions/workflows/deploy.yml) — последний build и deploy для `main` должны быть зелёными; workflow описан в [.github/workflows/deploy.yml](../../.github/workflows/deploy.yml).
- Открыть [https://anatolii-iumashev.github.io/medi/](https://anatolii-iumashev.github.io/medi/) напрямую, перезагрузить страницу и проверить консоль и Network: failed requests и обращений к несуществующим корневым `/audio`, `/icons`, `/manifest.webmanifest` быть не должно.
- Выполнить второй push с видимым безопасным изменением и убедиться, что новый зелёный deploy обновляет сайт без локальных override и персональных токенов.

### 5. Установка, offline и фон на реальных устройствах

- На актуальном Android/Chrome открыть опубликованный HTTPS URL и установить PWA нативным prompt или меню браузера. На актуальном iOS/Safari выполнить «Поделиться» → «На экран “Домой”» по [инструкции в интерфейсе](../../src/scripts/install.ts).
- После первого полного онлайн-открытия дождаться активации service worker, закрыть PWA, включить авиарежим и запустить её с домашнего экрана. Страница должна открыться, «Начать» и «Стоп» — работать без сети.
- Отдельно на каждой ОС запустить трек и проверить не менее 5 минут звука после сворачивания, затем ещё не менее 5 минут после блокировки экрана.
- Проверить название «Тихое дыхание», Medi, обложку и play/pause/stop в системном управлении там, где Media Session поддерживается. При звонке или потере аудиофокуса UI не должен показывать ложное воспроизведение.
- Очистить site data и повторить запуск офлайн: приложение не должно обещать готовый offline-режим до нового полного онлайн-открытия.

### 6. Обновление service worker

- При открытой предыдущей версии начать воспроизведение, опубликовать новую сборку и дождаться регистрации нового worker.
- Во время звучания не должно быть принудительного reload. После следующей навигации или перезапуска должна использоваться согласованная новая сборка, без смешивания старых и новых assets.
- Конфигурация обновления и очистки кэшей: [astro.config.mjs](../../astro.config.mjs).

### 7. Релизная проверка аудио и документации

- Подтвердить источник, владельца прав, лицензию и атрибуцию MP3; до этого [public/audio/meditation.mp3](../../public/audio/meditation.mp3) считается техническим placeholder, а релизный критерий остаётся открытым.
